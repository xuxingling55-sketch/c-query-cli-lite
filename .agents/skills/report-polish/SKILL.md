# 报告可读性优化

把一份"数据都在但没人想读"的分析报告，改写成"30 秒能抓住重点、5 分钟能看懂逻辑、需要时能查到细节"的文档。

## 硬约束（先读这条）

1. **不改任何数字、口径、结论方向。** 只允许重组结构、改写表述、增删解读性文字。如果发现原文数据自相矛盾，标注出来问用户，不要自行修正。
2. **输出方式按输入类型分流**：
   - 本地 Markdown 文件 → 在原文件同目录生成 `原文件名_v2.md`，不覆盖原文；用户明确要求覆盖时才覆盖。
   - 飞书文档（用户给出 docx/wiki 链接）→ 走下方"飞书文档分支"，在原文档上手术式修改，靠飞书版本历史兜底。
3. 正文中文，专有名词、字段名、代码保留英文。

## 工作流程

### 第 1 步：判断读者和用途

读完全文后，先确认这份报告是给谁看的。如果上下文能推断（如"发给老板的周报"）就直接推断，推断不了就问用户一句。读者决定详略：

- **管理层/横向同步**：结论和行动建议为主，证据表格进折叠或附录，全文压到原来的 1/2 以内。
- **业务同事/需要复核的**：保留完整证据链，但每张表前后必须有导读和解读。

### 第 2 步：诊断问题

对照下面的清单标出原文的问题，优化时逐条解决：

- [ ] 开头 3 行内能不能知道"发生了什么、多严重、该干什么"？
- [ ] 有没有一句话能概括全文？（没有就要提炼一个）
- [ ] 结论是判断句还是数据罗列？（"GMV 降 32.5%"是数据，"降幅主因是承接而非流量"才是判断）
- [ ] 单个段落里数字是否超过 3 个？（超过就该拆成表或删掉次要的）
- [ ] 每张表有没有回答"所以呢"？（表格后必须有一句解读）
- [ ] 表格列数是否超过 5 列？关键行有没有突出？
- [ ] 章节标题是"话题"还是"结论"？（"直播间数据"是话题，"直播间：进房和转化双降"是结论）
- [ ] 长句：一句话超过两个逗号且包含两个以上数字的，拆。
- [ ] 口径、数据说明等元信息是否混在正文里？（挪到文末附录）

### 第 3 步：按目标结构重写

```markdown
# 标题（含时间范围）

> 一句话总结：最核心的判断 + 最关键的一个数字。

## 先看结论

- 3~5 条。每条格式：**加粗的判断句。** 一两句支撑证据（最多 2 个数字）。
- 按重要性排序，不按分析顺序排序。
- 如有行动建议，单独一条放最后。

## 关键数字

| 指标 | 今年 | 去年 | 变化 |
（只放 3~5 个 headline 指标，让读者对盘子大小有概念）

## 分析正文（每节同构）

### 节标题 = 一句结论
先用 1~2 句话说这节要证明什么。
然后放证据（表格/数据）。
表格后用一句话解读：这张表说明什么、和上一节什么关系。

## 附录：口径与数据说明
（所有 SQL 字段、剔除规则、快照异常说明都放这里）
```

### 第 4 步：句子级改写规则

- **判断在前，数字在后**："付费用户下降快于流量，转化效率是主要问题（付费 -61.8% vs 活跃 -11.4%）"，而不是把数字塞在句子中间。
- **一段一个观点**。段落超过 4 行必拆。
- **加粗只给判断句**，不给数字加粗。满页加粗等于没有加粗。
- **删掉不改变结论的数字**。正文每保留一个数字都要问：删了它读者会误判吗？细节数字进表格或附录。
- **给对比一个锚点**："降幅 32.5%，约等于去年 1/3 的盘子没了"比裸百分比更有体感。
- 表格超过 7 行时，考虑：只保留 Top 行 + "其他"合计，或按结论相关性排序并加粗关键行。

### 第 5 步：交付

1. 写出 `_v2.md` 文件（飞书文档按下方分支处理）。
2. 向用户汇报 3 点：改动前后的结构对比（一两句）、你提炼的"一句话总结"（请用户确认判断是否准确）、有没有发现原文数据/逻辑存疑的地方。

## 飞书文档分支

输入是飞书文档链接时，诊断和改写规则（第 1~4 步）完全相同，读写方式换成 lark-doc 技能（依赖 lark-cli，操作前先读该技能的 SKILL.md 及其要求的参考文档）。**环境里没有 lark-cli 或 lark-doc 技能时降级**：把优化建议稿写成本地 `_v2.md` 交给用户自行粘贴。

操作规则：

1. **手术式修改，禁止 overwrite 全文重写**。先 `docs +fetch` 拿目录和目标 block ID，用 `block_replace` / `block_insert_after` 逐块修改；图片、画板、电子表格、`<cite>`、`<bookmark>` 等资源块一律不动。
2. **改前记录 revision_id**，交付时告知用户可通过飞书版本历史回滚。
3. **块编辑三个坑（每轮改完必须回读校验）**：
   - `block_replace` 会给块生成**新的 block ID**；对已不存在的旧 ID 再执行编辑会**静默返回成功但不生效**。同一块二次修改前必须重新 `docs +fetch --detail with-ids` 取当前 ID，改完用 fetch 回读核对关键词，不能只看命令返回值。
   - `<sheet>` 表格嵌入块不支持 `block_replace` 原地替换（静默无效）；要换表用 `block_insert_after` 插入新 sheet 块再 `block_delete` 删旧块。插入 sheet 块时飞书会把引用的工作表**克隆成新 sheet-id**，插入后要回读确认块数和内容。
   - 连续快速执行多个插入可能部分静默丢失；批量插入逐个执行并在每步后校验块数，失败重试。
3. **组件使用分寸**（遵循 lark-doc 的风格规范）：
   - 一句话总结用引用块（blockquote），不用高亮块。
   - 高亮块（callout）是强提醒信号，全文 0~2 个，只给口径说明、比较限制这类"不提醒会误读"的内容；原文已有的高亮块保留，不要再叠加。
   - 不为装饰上色；需要语义色时按 lark-doc 风格表选（信息蓝/警示红/注意黄）。
4. **典型修改动作**（按优先级）：压缩开头结论区的数字密度 → 给无标题挂靠的"孤儿段落"补章节归属（如文末散落的口径定义归入附录标题）→ 大表前加导读句 → 表格后补一句解读。
5. 交付汇报在第 5 步的 3 点之外，加一条：列出每处修改的位置和类型，方便用户在飞书里核对。

## 改写示例

**原文（数字密度过高）：**

> 截至 7 月 19 日，小低累计营收 1,186.94 万元，去年同期 1,365.46 万元，缺口 178.52 万元，同比下降 13.07%。相比 7 月 14 日，缺口只缩小 5.30 万元；相比 7 月 16 日，反而扩大 25.95 万元。

**改后（判断在前，次要数字收进括号或表格）：**

> **小低的营收缺口没有在收窄。** 截至 7 月 19 日累计缺口 178.52 万元（同比 -13.07%），比 7 月 16 日反而扩大了近 26 万元。
