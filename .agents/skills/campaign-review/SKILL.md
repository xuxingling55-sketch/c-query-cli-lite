# 活动复盘

从"活动结束"到"一份能对外同步的复盘报告"的完整流程。核心产出是判断，不是数据：每个环节都要回答"所以呢"。

## 硬约束

1. **所有数字必须有出处**：来自复盘数据包、仓库既有报告/CSV，或按 `knowledge/AI提示词.md` 口径新查的数据。禁止编造或从记忆里估数。
2. 新写 SQL 时严格遵循 `knowledge/` 口径（正价营收、活跃主表、去重规则等），先读 `knowledge/AI提示词.md` 再动手。
3. 报告落在 `reports/YYYYMMDD_<活动名>_复盘.md`。如需同步到飞书文档/多维表格，先问用户建在工作号还是个人号下。

## 工作流程

### 第 1 步：确认复盘框架

需要四项输入，缺什么问什么：活动名称、活动期（起止日期）、活动目标（金额或指标）、报告读者（管理层同步还是业务复核，决定详略）。

同比期默认整体前移一年、保持相同月日。

### 第 2 步：取数

优先走 review-data-pack skill（稳定脚本 `scripts/review_data_pack.py`），一次取齐 8 个模块：

| 模块 | 回答的问题 |
|---|---|
| overview | 总盘：营收、订单、付费用户、同比 |
| active_efficiency | 活跃规模与活跃转化效率 |
| user_stage | 用户分层（新增/老未/续费/高净值）× 学段 |
| product_structure | 商品结构（零售/组合品/续购，首购/复购） |
| deposit / reservoir | 定金、蓄水策略效果（未配置则标不适用） |
| high_value | 高净值用户表现 |
| sales_funnel | 销售漏斗 |

数据包覆盖不了的问题（如直播间漏斗、营销页漏斗、单日趋势），按 knowledge 口径补查，并把口径记入报告附录。

### 第 3 步：目标达成评估

先回答三个问题，再进归因：

1. 目标完成了多少？（实际 / 目标）
2. 和去年同期比是多少？（同比缺口或增量的绝对额 + 百分比）
3. 缺口/增量的趋势是什么？（活动期内分段看，缺口在收窄还是扩大；单日反弹不算收窄）

### 第 4 步：归因

用固定的分解框架，避免东一榔头西一棒子：

**主公式**：营收 = 活跃用户 × 付费转化率 × 客单价。先算三个因子各自的同比，回答第一个大判断——**是流量问题还是效率问题**：

- 付费用户降幅 > 活跃降幅 → 效率问题（承接/转化），继续往商品和漏斗拆。
- 活跃降幅 > 付费降幅 → 流量问题，往渠道和获客拆。
- 客单价上涨不等于健康：必须同时看交易频次，"单笔更贵但单数腰斩"是价格门槛问题。

**四个拆解轴**，逐轴找缺口集中度（哪个切片占总缺口 50% 以上）：

1. 渠道：电销 / APP / 新媒体 / 智课 / 平台电商
2. 学段：小低 / 小高 / 初中 / 高中
3. 用户分层：新增 / 老未 / 续费 / 高净值
4. 商品结构：零售 / 组合品 / 续购；首购 / 复购；价格带

拆解时的判断准则（来自历史复盘的经验）：

- 每个轴拆完要下一句"问题不是 X，而是 Y"式的判断，不能只列数字。
- 增量项（如高净值增长）要算够不够对冲缺口，不夸大亮点。
- 池子缩小和效率下降要分开说（"续费转化率在涨但续费活跃池 -35%"是两件事）。
- 累计和边际分开看：活动后期单独开窗口（如最近三天），判断措施是否起效。

### 第 5 步：定性证据（可选但强烈建议）

数据说"发生了什么"，定性材料说"为什么"。两类来源：

- 会议纪要 / 飞书文档中业务侧已有的判断，引用时注明来源。
- 沟通录音：如果当前环境安装了 comms-dataprep 和 speaker-attribution-prep 技能，用它们圈人拉录音、标说话人后抽样分析未成交原因；没有这两个技能时，请用户直接提供录音文本或纪要材料，或跳过本步并在报告中注明。分析方法：先随机小样本（约 10 条）验证归类框架，再全量归类，每类原因给出证据条数。

定性结论必须和定量缺口对得上（如"低价入口减少"应对应零售订单量数据）。

### 第 6 步：结论与建议

复盘四问，写进报告开头的结论区：

1. 目标定得对不对？（结果和目标差多少，差异来自目标还是执行）
2. 什么做对了？（有数据支撑的亮点，说明可否复制）
3. 什么做错了 / 没做够？（缺口主因，按贡献排序）
4. 下次怎么办？（3 条以内可执行建议，每条对应一个归因结论）

### 第 7 步：成文

产出分两层，句子规则都遵循 report-polish skill：

**本地工作稿**（默认必产出）：写到 `reports/YYYYMMDD_<活动名>_复盘.md`，结构为一句话总结 → 先看结论 → 关键数字表 → 分析正文（每节"结论标题 + 证据 + 解读"）→ 附录（口径、数据来源、数据包链接）。

**飞书正式复盘文档**（用户要求同步时产出，先问工作号还是个人号）：不套工作稿结构，按团队正式复盘模板组织（参照往期范例 [2025.7 冲顶暑促私域业务复盘](https://guanghe.feishu.cn/docx/B1EQd91NZoGKgjxiSjgcF5G0nye)）：

1. **顶部"营收完成情况"高亮卡**：总营收与完成率、分渠道拆分（销售/APP）、同比（写法统一为「去年值，±%，±绝对额万元」）、目标位（有激进/保守双目标就都列）、服务期营收口径单列。
2. **一、私域经营分析**：
   - 总判断 callout：用主公式（活跃 × 转化 × 客单 → ARPU → 营收）一段话讲清本次盈亏的结构原因。
   - ‼️关键信息‼️三段 callout：**正向收益**（🤗）、**负向影响**（🤯）、**需要特别关注**（❗）。每条尽量量化营收影响（如"流量 -72 万 × 单用户价值 25 元 ≈ -1,810 万"），亮点要说明可否复制，风险要区分一次性还是趋势性。
   - **讨论区 callout**（🗣️）：3~5 个开放问题供管理层会上讨论，每个问题带数据依据，不给结论。
   - 详细数据：关键表格；有数据包飞书表格就嵌入或链接。
3. **二、渠道分析**：销售、APP 各自的关键结论；有渠道专项复盘文档就用 cite 引用。
4. **附：数据与口径**：数据包链接、口径说明、检查摘要、未覆盖项（如日粒度趋势）。

交付时向用户汇报：报告路径 / 文档链接、一句话总结（请用户确认判断）、数据上存疑待复核的点。

## 快速检查

| 情况 | 动作 |
|---|---|
| 缺活动名称/日期/目标/读者 | 只问缺失项 |
| 数据包模块失败或不适用 | 在报告附录如实标注，不虚构 |
| 数字对不上历史报告 | 停下来核对口径，标注差异原因 |
| 用户要发飞书 | 先问工作号还是个人号 |
| 只有单日改善 | 写"单日反弹"，不写"趋势收窄" |
